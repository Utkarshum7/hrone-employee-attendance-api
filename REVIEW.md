# REVIEW.md

Findings in the starter `app/main.py`. Each is addressed in the submitted `app/main.py`. Line numbers refer to the original starter file. Each row is tagged with its type (defect, missing feature, performance problem, contract violation, ...).

How each finding was established: rows 1-5 and 15 were **reproduced by executing the starter's helper functions** (copied verbatim) with the inputs shown; the other rows come from reading the starter code against the contract and, where noted, were not executed. The corrected rules are covered by tests in `tests/`.

| # | Where (function / line) | What is wrong | How you'd notice it | How I fixed it |
|---|---|---|---|---|
| 1 | `compute_late_minutes` (l.33-37) | **[Defect]** `punch_in.replace(hour=h, minute=m)` builds the shift start in the datetime's *own* zone (naive local / UTC), but shift times are IST. Wrong start on any server not running in IST. | Reproduced: server in UTC, shift 09:30, punch 10:00 IST (= 04:30 UTC naive): the starter returns 0, the contract gives 30. | Shift start is built as an IST instant on the attendance date (`at_ist`), then subtracted. |
| 2 | `compute_late_minutes` (l.36-37) | **[Defect]** Grace check is done on already-floored whole minutes (`int(seconds/60) > 10`), so 09:40:01 .. 09:40:59 floor to 10 and are treated as on time. Sub-second values are not truncated either. | Reproduced: shift 09:30, punch 09:40:01 -> starter returns 0, R2 says 10. | Compare the *seconds* (`> 600`), then floor to minutes. Instants are truncated to whole seconds on input. |
| 3 | `compute_late_minutes` / `punch_in` | **[Defect (missing rule)]** No overnight handling: for a 22:00-06:00 shift a punch at 03:00 gets today's date and a start of 22:00 *today*. R1 says it belongs to yesterday's shift. | Reproduced: 22:00 shift, punch 03:00 -> starter late = 0 (R1/R2 give 300 minutes, attendance date the previous day); the starter files it under the punch's own date. | `attendance_date()` applies R1; `late_minutes` is measured from the shift start on that attendance date. |
| 4 | `compute_work_hours` (l.40-41) | **[Defect]** Python `round()` on a float: banker's rounding plus binary float error, and no whole-second truncation. R4 requires half-up. | Reproduced: 54 s of work = 0.015 h; the starter returns 0.01, R4 (half-up) gives 0.02. | Integer seconds -> `Decimal` -> `quantize(0.01, ROUND_HALF_UP)`. |
| 5 | `compute_overtime` (l.44-47) | **[Defect]** Shift end is built from `date_str`'s own day, so an overnight shift's end lands on the wrong day (the day *before* the punch-out) and the overtime is huge/negative. No 30-minute minimum: 1-29 minutes are returned as overtime. | Reproduced: shift end 18:00, out 18:10 -> starter returns 10, R3 says 0. Overnight shift end 06:00, out 07-07 06:40 -> starter returns 1480, R3 says 40. | Shift end is the attendance date at `shift_end`, plus one day for overnight shifts; only >= 30 whole minutes count. |
| 6 | no punch-out endpoint (l.153-162 TODO list) | **[Missing feature]** The starter's own TODO list names `POST /attendance/punch-out` but it was never written, so the `compute_overtime` helper is never called. Unfinished work, not a defect in existing behaviour; the helper itself is reviewed in row 5. | `POST /attendance/punch-out` is 404/405. | Implemented punch-out (R3-R5, race-safe). |
| 7 | `EmployeeIn` (l.53-60) | **[Defect (missing validation)]** No validation: any `emp_code`, any shift string, `shift_start == shift_end`, invalid `joined_on`, no length limits. | `{"shift_start": "banana"}` is accepted and later crashes `compute_late_minutes` with a 500. | Patterns/lengths from the contract, date check, `shift_start != shift_end` validator -> 422. |
| 8 | `PunchInIn` (l.63-66) | **[Defect (missing validation)]** `status` is any string (`ABSENT` accepted); `punched_at` is a lax pydantic `int`, so (checked with pydantic 2) `true`, `1783312500000.0`, the string `"1783312500000"`, negatives and seconds-looking values are all accepted. | `{"status": "ABSENT"}` creates an "absent" record with a punch-in. `punched_at: 1783312500` (seconds) is silently treated as 1970. | `Literal[PRESENT, WFH, ON_DUTY]`, `StrictInt` between 1e11 and 4102444800000. |
| 9 | module top (l.22-23) | **[Defect (reliability)]** `MongoClient` without `tz_aware=True`: every datetime read back is naive. No server-selection timeout (PyMongo's default server-selection timeout is 30 s, so requests hang that long when MongoDB is down). | Comparing a stored datetime with an aware one raises `TypeError`; stopping MongoDB makes every call hang. | `tz_aware=True`, short `serverSelectionTimeoutMS`, DB errors mapped to 503. |
| 10 | no index creation | **[Missing requirement / performance]** The contract requires all indexes at startup; none exist, so every query is a collection scan and uniqueness is not enforced. | `explain` on the list query shows COLLSCAN (the kit's data model says only `_id` is indexed); duplicates are possible. | `ensure_indexes()` in the startup lifespan (idempotent). |
| 11 | `health` (l.72-74) | **[Defect]** Always returns ok, even when MongoDB is down. | Stop MongoDB: `/health` still says 200, so a runner polling it (as the contract says it does) would start testing too early. | Pings MongoDB; 503 on failure. |
| 12 | `create_employee` (l.77-85) | **[Defect (race condition)]** Check-then-insert (`find_one` then `insert_one`) with no unique index: parallel creates can both pass the check and both insert (reasoned from the code, not executed). `created_at` is `datetime.now()` (naive, server-local) and is returned as a datetime, not epoch ms. | Parallel POSTs with the same `emp_code` can yield several 201 (not run against the starter). | Unique index on `emp_code`; `insert_one` and catch `DuplicateKeyError` -> 409. `created_at` stored as UTC datetime, returned as epoch ms. |

| 15 | `punch_in` (l.102-103) | **[Defect]** `datetime.fromtimestamp(ms/1000)` uses the *server's* local zone and `if body.punched_at` treats `0` as "missing"; `.date()` is therefore not the IST date (R1). | Server in UTC, punch at 00:30 IST: starter files it under the previous day. | `ms_to_dt()` (UTC, truncated to seconds) and `attendance_date()` (IST). |
| 16 | `punch_in` (l.104-118) | **[Defect (race condition)]** Check-then-insert race: two simultaneous punch-ins can both pass `find_one` and both insert (reasoned from the code, not executed). | Parallel identical punch-ins can create duplicate documents (not run against the starter). | Unique `(emp_code, date)` index; `insert_one` + `DuplicateKeyError` -> 409. | 20 | whole file | **[Robustness weakness]** Unhandled `pymongo` errors surface as a plain 500 "Internal Server Error" (the traceback goes to the server log). | MongoDB down -> 500 instead of a clear 503. | App-wide handler returns 503 `{"detail": "database unavailable"}`. |

## Looked at and judged fine

- `IST = timezone(timedelta(hours=5, minutes=30))` is correct (IST has no DST).
- `load_dotenv()` with its default `override=False` already lets real environment variables win over `.env`, as the contract asks.
- `doc.pop("_id")` in `create_employee`: `insert_one` adds `_id` to the dict in place, so popping it is needed and correct.
- Comparing `date` strings with `$gte/$lte` is correct because `YYYY-MM-DD` sorts lexicographically.
- Returning 201 for punch-in and employee creation matches the contract.
